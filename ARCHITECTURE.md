## 1. What Is MVMCareSync?

MVMCareSync is an internal operations platform for managing **vendor coverage at Ambulatory Surgery Centers (ASCs)**.

When a surgery is scheduled, an ASC needs to confirm that the right vendor (an anesthesia group, a CRNA backup, a neuro-monitoring technician, a device rep, etc.) will be present. Today this is done via phone calls, texts, and spreadsheets — which breaks down at scale.

MVMCareSync replaces that process with a structured **Case Request** workflow: create a request, assign a vendor, confirm attendance, and keep an immutable audit trail of every status change. All outbound vendor communications are sent via email automatically.

## 2. Who Uses It

| Role        | Who they are                                              | Portal access |
|-------------|-----------------------------------------------------------|:-------------:|
| Admin       | IT / operations manager — full system control             | ✓             |
| Coordinator | Scheduling coordinator — owns the request lifecycle       | ✓             |
| Staff       | ASC staff / OR schedulers — creates and submits requests  | ✓             |
| Read-only   | Finance / auditors — view-only access                     | ✓             |
| Vendor      | External vendor companies                                 | ✗             |

> **Vendors do not have portal logins in v1.** They are contacted exclusively via email (request, cancellation, and reminder emails generated by the system).

## 6. Database Schema

All tables (except `users`) extend `TimeStampedModel` which adds:
- `id` — UUID primary key, auto-generated
- `created_at` — timestamp set on insert
- `updated_at` — timestamp updated on every save

### 6.1 `users`

Extends Django's `AbstractUser` (inherits `username`, `email`, `first_name`, `last_name`, `password`, `is_active`, `is_staff`, `last_login`, `date_joined`). Table name: `users`.

| Column       | Type        | Notes                                          |
|--------------|-------------|------------------------------------------------|
| id           | int (auto)  | Django default PK for AbstractUser             |
| username     | varchar     | Unique login handle                            |
| email        | varchar     | Contact email (used for password reset)        |
| first_name   | varchar     |                                                |
| last_name    | varchar     |                                                |
| role         | varchar(20) | `admin` / `coordinator` / `staff` / `readonly` |
| department   | varchar     | Optional — e.g. "OR Scheduling"                |
| phone        | varchar     | Optional                                       |
| is_active    | bool        | Deactivated users cannot log in                |
| password     | varchar     | Hashed by Django                               |

**Computed properties (not stored):**

| Property        | Returns true when                               |
|-----------------|-------------------------------------------------|
| `is_admin`      | role == `admin`                                 |
| `is_coordinator`| role == `admin` OR `coordinator`                |
| `is_readonly`   | role == `readonly`                              |
| `full_name`     | `get_full_name()` or `username`                 |

### 6.5 `vendor_coverage_rules`

Maps which vendors are eligible for which facility + service type combinations. Owned by the `case_requests` app. Used by the `match_vendors()` function to populate the assignment dropdown.

| Column       | Type | Notes                                              |
|--------------|------|----------------------------------------------------|
| id           | UUID |                                                    |
| vendor       | FK   | → `vendors.id`                                     |
| facility     | FK   | → `facilities.id`                                  |
| service_type | FK   | → `service_types.id`                               |
| is_preferred | bool | Preferred vendors surface first in dropdowns (★)   |
| notes        | text |                                                    |
| is_active    | bool |                                                    |

**Unique constraint:** `(vendor, facility, service_type)` — one rule per combination.

**Matching algorithm** (`apps/case_requests/matching.py`):
1. Filter rules by `facility`, `service_type`, `is_active=True`
2. For each rule, check `vendor.is_bookable`
3. Sort: preferred first, then alphabetical by vendor name
4. If exactly 1 bookable result → `auto_selected` is set in the API response

### 6.6 `case_requests`

The central table. One row = one vendor coverage request for one case.

| Column             | Type     | Notes                                                      |
|--------------------|----------|------------------------------------------------------------|
| id                 | UUID     |                                                            |
| request_date       | date     | The date of the scheduled case                             |
| facility           | FK       | → `facilities.id`                                          |
| service_type       | FK       | → `service_types.id`                                       |
| vendor             | FK/null  | → `vendors.id` — null until assigned; cleared on backup_needed |
| procedure_type     | varchar  | e.g. "Lumbar Fusion"                                       |
| arrival_time       | time     | Vendor expected arrival                                    |
| start_time         | time     | Case start time                                            |
| end_time           | time     | Estimated end time                                         |
| patient_identifier | varchar  | **PHI-safe: initials or case ID only — no full name/DOB/MRN** |
| surgeon_provider   | varchar  | Surgeon name                                               |
| notes              | text     | General notes                                              |
| requester          | FK       | → `users.id` — who created this request                    |
| status             | varchar  | See status values below                                    |
| confirmation_notes | text     | Notes added when coordinator confirms                      |
| created_at         | datetime |                                                            |
| updated_at         | datetime |                                                            |

**Status values:**

| Value                   | Label                 | Entry point                          |
|-------------------------|-----------------------|--------------------------------------|
| `draft`                 | Draft                 | On creation                          |
| `requested`             | Requested             | After `submit` action                |
| `vendor_responded`      | Vendor Responded      | Manual status update (future)        |
| `confirmed`             | Confirmed             | After `confirm` action               |
| `backup_needed`         | Backup Needed         | After `backup_needed` action         |
| `credentialing_pending` | Credentialing Pending | Coordinator sets while waiting       |
| `cancelled`             | Cancelled             | After `cancel` action (any status)   |
| `completed`             | Completed             | After `complete` action (confirmed only) |

## 8. Request Lifecycle

```
           Staff / Coordinator
                  │
                  ▼
             ┌─────────┐
             │  DRAFT  │  ← Created by staff or coordinator
             └────┬────┘
                  │  submit()  →  vendor request email sent
                  ▼
           ┌───────────┐
           │ REQUESTED │  ← Awaiting vendor confirmation
           └─────┬─────┘
                 │
        ┌────────┴────────────────────────────┐
        │                                     │
        │ assign_vendor + confirm()           │ backup_needed()
        │ → requester email + Teams alert     │ → vendor field cleared
        ▼                                     ▼
  ┌───────────┐                   ┌──────────────────────┐
  │ CONFIRMED │                   │    BACKUP NEEDED     │
  └─────┬─────┘                   └──────────┬───────────┘
        │                                    │ assign new vendor
        │                                    │ + confirm()
        │                                    ▼
        │                            ┌───────────┐
        │                            │ CONFIRMED │
        │                            └─────┬─────┘
        │                                  │
        └──────────────┬───────────────────┘
                       │  complete()
                       ▼
                 ┌───────────┐
                 │ COMPLETED │  (terminal)
                 └───────────┘

  ── Special paths ──────────────────────────────────────────────
  REQUESTED → VENDOR_RESPONDED  (vendor has replied, awaiting final confirm)
  REQUESTED → CREDENTIALING_PENDING  (vendor needs cred approval first)
                    │
                    ▼
               CONFIRMED

  ── Cancel (from any non-terminal status) ──────────────────────
  Coordinator / Admin → cancel()
                  │  reason required, recorded in history
                  │  → vendor cancellation email sent
                  ▼
           ┌───────────┐
           │ CANCELLED │  (terminal)
           └───────────┘
```

Every transition writes one row to `request_status_history`.

> **Note:** `backup_needed` can only be triggered from `REQUESTED` or `VENDOR_RESPONDED` status. The vendor FK is set to `null` when this action fires.

## 10. Email & Notifications

### Email backend

Emails are sent via the **Mailtrap REST API** (`apps/common/email_backend.py`). The `EMAIL_BACKEND` env var points to this class. In development, all emails are captured in the Mailtrap sandbox inbox.

### Trigger map

| Event                    | Celery task                     | Recipient(s)                     | Notification type |
|--------------------------|---------------------------------|----------------------------------|-------------------|
| Request submitted        | `send_vendor_request_email`     | Vendor primary + backup email    | `email`           |
| Request cancelled        | `send_vendor_cancellation_email`| Vendor primary + backup email    | `email`           |
| Request confirmed        | `notify_team_on_confirm`        | Requester email                  | `email`           |
| Any of the above         | (same tasks)                    | MS Teams channel (if webhook set)| `teams`           |
| Pending within 48h (beat)| `send_pending_reminders`        | Requester email                  | `internal`        |

### Celery beat schedule

`send_pending_reminders` runs every **8 hours** (configured via `django_celery_beat` database scheduler). It sweeps for requests in `REQUESTED` or `BACKUP_NEEDED` status with `request_date` within the next 48 hours and sends a reminder to the requester — skipping any request that already received a reminder today.

### Retry policy

- `send_vendor_request_email`: 3 retries, 60s delay
- `send_vendor_cancellation_email`: 3 retries, 60s delay
- `notify_team_on_confirm`: 2 retries, 30s delay

All failures are logged to `notification_logs` with `status = 'failed'` and an `error_message`.

## 13. End-User Use Cases

---

### Use Case 1 — Staff creates a vendor coverage request

**Who:** ASC staff member (e.g. OR scheduler)  
**When:** A surgeon blocks an OR case that requires an outside vendor

**Steps:**
1. Log in → sidebar shows **New Request** (hidden for read-only users)
2. Go to **Requests → New Request**
3. Pick the facility, case date, and service type
4. Enter procedure type, surgeon name, and patient identifier *(initials or case ID — no full name, DOB, or MRN)*
5. Set arrival time and estimated start/end times
6. Save as **Draft** — no one is notified yet
7. Review and click **Submit** — status moves to `Requested`; a vendor request email is sent if a vendor is already assigned

---

### Use Case 2 — Coordinator assigns a vendor and confirms

**Who:** ASC Coordinator  
**When:** A request arrives in `Requested` status

**Steps:**
1. Open the request from the **Requests** list
2. In the Assignment panel, pick a vendor from the dropdown — preferred vendors (★) are listed first, based on coverage rules
3. If only one bookable vendor matches, the system auto-selects it
4. Contact the vendor externally to verify availability
5. Click **Confirm**, enter confirmation notes
6. Status moves to `Confirmed` — the requester receives a confirmation email; Teams is notified if configured

---

### Use Case 3 — Vendor is unavailable, backup needed

**Who:** ASC Coordinator  
**When:** Assigned vendor cannot cover the case

**Steps:**
1. Open the confirmed (or requested) request
2. Click **Backup Needed** — the vendor is cleared from the request, status moves to `Backup Needed`
3. Reassign a different vendor from the dropdown
4. Contact the new vendor to confirm
5. Click **Confirm** → status returns to `Confirmed`

---

### Use Case 4 — Case is completed

**Who:** ASC Coordinator or Admin  
**When:** The case date has passed and the vendor attended

**Steps:**
1. Find the `Confirmed` request for that date
2. Click **Complete** — status moves to `Completed`
3. The full history (every transition, who made it, timestamps, notes) is preserved on the detail page

---

### Use Case 5 — Request is cancelled

**Who:** ASC Coordinator or Admin  
**When:** A surgery is postponed or cancelled

**Steps:**
1. Open the request (any non-terminal status)
2. Click **Cancel**, enter the reason (e.g. "Patient cancelled — rescheduling")
3. Status moves to `Cancelled` — reason and timestamp are saved to history
4. If a vendor was assigned, a cancellation email is sent to the vendor

---

### Use Case 6 — Coordinator adds a new vendor

**Who:** ASC Coordinator or Admin  
**When:** A new vendor company is contracted

**Steps:**
1. Go to **Vendors → Add Vendor**
2. Fill in company name, service type, primary and backup contact details
3. Set contract status (`Active`) and credentialing status (`Approved` or `Pending`)
4. In the Coverage Rules section, link the vendor to the relevant facilities and service types
5. Mark a combination as **Preferred** if this vendor is the first choice there
6. The vendor now appears in coordinator dropdowns for matching requests

---

### Use Case 7 — Admin manages user accounts

**Who:** Administrator  
**When:** A new employee joins or a staff member leaves

**To create an account:**
1. Go to **Users → Add User** (admin-only route)
2. Enter name, email, username, and assign role
3. Set a temporary password; user can change it at `/profile`

**To deactivate an account:**
1. Open the user in the **Users** list
2. Uncheck **Active** — the user can no longer log in; their request history is preserved

---

### Use Case 8 — Read-only auditor reviews history

**Who:** Finance or compliance reviewer (read-only role)  
**When:** Monthly audit or on-demand review

**Steps:**
1. Log in — all write actions are hidden (no submit, confirm, assign, cancel buttons)
2. Browse the **Requests** list, filter by facility, date range, or status
3. Open any request to see the full **Status History** panel: every transition, who made it, timestamps, and notes
4. The **New Request** link is absent from the sidebar; navigating to `/requests/new` directly redirects back to `/requests`
5. No data can be created or modified

---

*PHI constraint enforced system-wide: `patient_identifier` stores patient initials or a case ID only. Full patient names, dates of birth, and MRNs are never stored in this system.*
